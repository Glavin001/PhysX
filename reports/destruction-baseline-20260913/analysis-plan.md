# Analysis and next optimization decisions

2026-09-13. **Working plan while the new baseline collection runs.** This is not a claim that all data has been collected or an authorization record for changing numerical acceptance. No optimization is implemented in this campaign.

## What the guides change about the investigation

Both supplied guides were read in full: *CUDA Performance Handbook* (1,736 lines) and *CPU/GPU CUDA Optimization Guide* (1,307 lines). Their recommendations are engineering hypotheses, subordinate to the requested simulation semantics. Copies and hashes are preserved in `evidence/guides/`.

The key distinction is between removing work and executing the remaining work more efficiently. We will measure complete accepted ticks and separately account for asset preparation, first use, changes in topology and persistent memory. GPU occupancy, instruction counts, library solve times and iterations are mechanism evidence. None is an application speedup by itself.

An intact asset has a much longer lifetime than a contact load. Coefficients, geometry and reusable solver structure can be prepared at load time; current contacts, accumulated damage, fracture and correction cannot be moved to a later tick. A previously converged equilibrium does not imply that damage has stopped accumulating. Reuse needs an explicit validity condition for each product, rather than one broad “unchanged island” flag.

The existing implementation already keeps numerical work on the GPU, runs component iterations without a CPU round trip per iteration, dynamically distributes components, reuses some exact settled solves, and preserves geometry across ownership changes. These are not new optimization opportunities. N20's retained capacity change is already in the frozen control. The selected commit's `gatherCorrectionOwnerMetadata` also already publishes a compact GPU-validated correction work set: unrelated owners and physical state are not indiscriminately read back at that bridge. Further sparse-publication proposals must identify a different remaining producer/consumer cost.

## Factor and Tile constraints

For cuDSS, analysis is synchronous; factorization/solve can be asynchronous under supported configurations. Graph use requires compatible allocation, and default solves are not bitwise reproducible. These are integration constraints to test, not reasons to insert a host wait into each stress pass. See [NVIDIA's cuDSS lifecycle and graph documentation](https://docs.nvidia.com/cuda/cudss/general.html). The existing captured factor tests establish feasibility only; they do not qualify material decisions or the complete simulation.

[CUDA Tile IR](https://docs.nvidia.com/cuda/tile-ir/latest/index.html) is an explicit tile programming target, not an automatic optimizer for the entire C++ destruction pipeline. A native FP64 probe already compiles for this GPU; there is no integrated solver speedup. Consider it only after identifying regular necessary work with suitable data layout, and benchmark all conversion/setup costs.

## Acceptance and stopping rules

Hold the 52 inputs, current-tick contact ordering, sleeping, ordinary API, 1/60 timestep and at most one correction fixed. Restore and observation export remain outside tick timing. Include current setup/growth, synchronization and final publication. Every candidate receives a separate commit, exact hypothesis, native numerical/physical/memory evidence, repeated A0/B/A1 light screen, confirmation where drift matters, then all52 and continuous idle/heavy qualification if it survives. Save raw repetitions and first-use peaks.

Do not call unchanged work counters complete trajectory correctness. The existing test audit identifies independent material-margin and long-run orientation/velocity gaps; retain them explicitly while the separate test-contract work proceeds. Never silently switch this campaign's frozen checker to concurrent workspace changes. Any deliberate precision compromise needs the physical quality contract first, not a relaxed test after a failure.

After three failures in a family, review the diagnosis and relevant implementations before another candidate. Preserve the best verified implementation. There is no evidence for a physically optimal final solution yet: large restored debris and continuous heavy simulation still exceed the real-time budget substantially.
