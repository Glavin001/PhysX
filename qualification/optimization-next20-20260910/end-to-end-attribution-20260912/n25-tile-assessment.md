# CUDA Tile assessment after local-row experiment

CUDA Tile is available but is not integrated into this solver. The installed CUDA13.4.59 compiler successfully compiled an FP64 Tile C++ probe forsm120; this establishes compiler availability only. Exact command, compiler version and source/object hashes: `out/end-to-end-attribution-20260912/tile-availability/receipt.json`.

NVIDIA's [Tile IR introduction](https://docs.nvidia.com/cuda/tile-ir/latest/sections/introduction.html) describes an explicit tile programming model with CUDA C++/PTX interoperability. The [optimization guide](https://docs.nvidia.com/cuda/tile-ir/latest/sections/optimization_guide.html) assigns instruction selection, pipelining, resource allocation and warp specialization to the compiler, with advisory per-architecture hints. It still requires the programmer to express tile operations and partition the computation; it does not infer destruction-state validity, remove redundant application stages, or change the solver algorithm for us.

The current [release notes](https://docs.nvidia.com/cuda/tile-ir/latest/sections/release_notes.html) include gather/scatter views, strided views and view-based atomic reduction. Therefore irregular graph access is not a categorical reason to rule Tile out. These specification capabilities do not establish that every operation is supported by our chosen C++ frontend, nor that sparse six-coordinate FP64 operations will be faster. Test the exact operation before planning a port.

N25 provides a useful constraint: expressing eight cooperative tiles sequentially inside one component was redundant work, and removing it cut the rejected bridge kernel's executed instructions from681.4M to49.2M. The resulting complete tick still loses to the retained control across bridge, chain, impact, large idle and debris. Porting that entire rejected cycle to Tile without revisiting its cost would start from the wrong application baseline. [All unprofiled scenario metrics and quality failures](n25-screen.md).

A justified Tile experiment should select a surviving, measured operation; include gathers, packing/padding, factor construction, graph integration and any numerical refinement; compare full ticks against the retained implementation; and preserve current-contact stress, at most one correction and the second stress evaluation. Tensor-core or narrower arithmetic needs independent equilibrium/force/material checks, not just a lower residual or fewer iterations. Kernel timing alone is not acceptance.

Next ownership decisions must also respect the existing work census: the solver already dynamically claims components, and largest-city recorded CTA durations are reasonably balanced. The data supports neither an automatic Tile speedup nor a universal straggler explanation. [Existing-record audit](n25-retained-balance.json). Conditional preparation, localized topology and fragment lifecycle removal remain separate ranked opportunities.
