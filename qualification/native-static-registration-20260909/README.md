# GPU rigid/static registration ordering — isolated prototype, integration pending

Ranked replacement 1 remains incomplete. This work is a tested storage/ordering
prototype plus a complete **unapplied review patch**, not a production migration
or a performance improvement. The production baseline remains a6a0562a.

## Responsibility and evidence

The native rigid/static path currently owns per-body contact and joint arrays in
`PxgBodySimManager`. Adds append; removals perform an order-preserving shift.
`PxgGpuContext::doStaticRigidConstraintPrePrep` scans those arrays for active
bodies and builds strided indices; PGS/TGS upload the arrays to GPU batching.
This is a CPU registration consumer which has to disappear before GPU fragment
registration can stand independently of CPU compatibility objects.

The prototype assigns insertion sequences on GPU, groups lifecycle commands by
registration ID using a stable radix sort, and processes distinct registrations
in parallel. Only changes to the same registration serialize. Stable sequence
and owner sorts build GPU-owned ranges; active-body gathering produces the
existing solver layout. Removal does not shift a CPU list. Reused IDs receive a
new insertion sequence. Contact and joint order is checked independently against
CPU vectors with actual stable erase operations, not a duplicate of the GPU sort.

The original standalone GPU allocator in `PxgDestructionRegistration.cuh` is a
separate unfinished part of motion/contact lifetime work; this test does not
claim to integrate that allocator or solve dynamic-contact activation ordering.

## Isolated tests

- 513 node slots / 4,099 registration slots / 24 deterministic command batches.
- 113,664 node slots / 32,768 registration slots / four deterministic batches.
- One node with 4,099 contacts, partial removal and same-batch reuse as joints.
- Growth, empty membership, unchanged submission, active-order permutation,
  inactive-node exclusion, full retirement and explicit stale/duplicate/invalid
  command failures. Failed command transactions latch rejection.
- Independent membership, insertion order and aggregate checks pass.
- Four CUDA sanitizer tools are recorded separately; see `extended-*.log`.

These are **registration fixtures: no rigid-body integration, chunks, stress
bonds, projectiles or correction passes are simulated**. They are not a 256-city
performance test and cannot establish physical trajectory or 60/120 Hz behavior.
The initial prototype source/binary hashes and source archive preserve the first
sanitizer campaign. The extended oracle adds the high-degree case and removes
compiler narrowing warnings. Initial source warnings were not runtime failures.

## Proposed integration (not applied)

`integration-review.patch`, reproducibly generated by
`prepare-integration-patch.py`, proposes:

1. GPU ownership of rigid/static lists; CPU partitioning emits ordered deltas.
2. One-time adoption of existing rigid lists when destruction is attached;
   articulation-specific lists retain their ordinary upstream implementation.
3. Removal of native CPU list preparation and the corresponding PGS/TGS uploads.
4. GPU generation of actual solver batching inputs in the solver stream.
5. A private runtime ABI increment; ordinary public destruction API unchanged.
6. Explicit failure handling and a CMake target using the production kernel.

The patch passes `git apply --check` only. **It has not been applied, compiled,
linked or run.** Its real PxNodeIndex adapter, device-fault handling, existing-scene
adoption, task-graph placement and PGS/TGS consumers still require integrated
validation. The standalone tests do not qualify those additions.

Remaining costs/tradeoffs are explicit: CPU partitioning still submits commands;
GPU stats still require a small completion receipt for host solver capacities;
changed registrations currently rebuild global sorted ranges. These must not be
reported as a complete GPU lifecycle, selective topology or eliminated host waits.
No speed prediction is justified before matched idle/destruction screens.

## Approval boundary

Automatic approval review rejected two attempts to edit the core integration.
The first cited breadth and incomplete adoption code. After the isolated tests,
the second still rejected the runtime/interface integration as too broad and
unvalidated. Neither attempted script executed; production source stayed unchanged.
A complete review-only patch was then generated successfully, and explicit user
approval was requested before applying and qualifying it. This is an automatic
review boundary, not an additional SKILL.md requirement or missing original intent.

For context, the intended main performance workload remains 256 buildings,

## Reproduction and storage

The prototype compiles independently with CUDA 12.8 using:

```
/usr/local/cuda/bin/nvcc -std=c++17 -O2 -lineinfo -arch=sm_89 \
  physx/source/gpudestruction/tests/static_registration_prototype_test.cu \
  -o out/native-static-registration-20260909/static_registration_extended_test
out/native-static-registration-20260909/static_registration_extended_test
```

The filesystem was nearly full. `ram-link-inputs.json` records content-hash-verified
relocation of generated link inputs to `/dev/shm`; no source, service, executable
or evidence was removed. Those link inputs need rebuilding if RAM disappears.
